# Жалобы, апелляции и Discord

Обновление устанавливается вместе с LoveCore из ветки `feat/discord-moderation`. Обновлённый WebAdmin использует Discord API v2, старые потребители LoveCore сохраняют доступ к прежним методам.

## Подключение

1. Установите парные JAR LoveCore и LoveWebAdmin после остановки сервера.
2. В LoveCore настройте `discord.enabled`, `bot-token`, `guild-id`, `appeals-category-id`, `staff-role-ids`. Боту нужны права просмотра и истории сообщений, отправки сообщений, вложений и управления каналами; при приглашении — scopes `bot` и `applications.commands`. В Developer Portal включите Message Content Intent для чтения текста тикетов через REST. Кнопки и формы поступают через Gateway.
3. В WebAdmin укажите `web.public-url` (HTTPS-адрес панели), `discord.reports-channel-id` и `discord.appeals-channel-id`.
4. У сотрудника ник учётной записи WebAdmin должен соответствовать Minecraft-аккаунту в истории игроков. Подтвердите привязку Minecraft → Discord через LoveCore/LoveAuth. Ручной Discord ID из прежних настроек больше не предоставляет идентификацию и не используется для доставки служебных ЛС.
5. Выдайте необходимые новые права через редактор ролей. Пользовательские изменения существующих ролей теперь сохраняются при запуске.

## Игрок

После блокировки, успешно применённой через WebAdmin, привязанный игрок получает личное сообщение с причиной, сроком, источником и кнопкой апелляции. Ошибки доставки видны на `/deliveries.html` (ссылка в настройках Discord) с правом `MANAGE_API`; временные ошибки повторяются, после шести попыток запись получает `FAILED`. Передача в Discord имеет семантику at-least-once: уникальный ключ события и Discord nonce подавляют обычные повторы, но абсолютная гарантия exactly-once через сбой сети/процесса не заявляется.

Команда Discord `/апелляция` открывает форму. Для привязанного аккаунта ник определяется автоматически. Для непривязанного вводится ник, обращение отмечается неподтверждённым. Тикет доступен его создателю и указанным ролям персонала. Знание ника не открывает переписку и не создаёт привязку.

Веб-страница `/appeal.html` позволяет подать апелляцию без Discord. Автор получает случайный ключ доступа; в БД хранится его SHA-256. Ссылка из Discord передаёт ключ во фрагменте URL, затем страница убирает его из адреса и хранит в sessionStorage. Старые апелляции без ключа остаются доступны персоналу; прежний доступ по одному нику закрыт намеренно. Не публикуйте авторские ссылки.

## Персонал

- В существующем списке жалоб есть переход «Работа с делом»; в апелляции — «Ответственный, заметки и решение».
- `/case.html?kind=report&id=12` и `/case.html?kind=appeal&id=12` открывают служебное рабочее место. Поддерживаются взятие, передача, приоритет, ожидание ответа и внутренние заметки.
- Внутренние заметки не включаются в публичные ответы и не пересылаются в Discord.
- Решения панели и Discord используют один `AppealService`, резервирование состояния и обязательное обоснование. При невозможности снять бан апелляция не объявляется одобренной.
- Закрытый Discord-канал переводится в режим чтения, а не удаляется. Пользователи с Discord Administrator могут обходить channel overwrites по правилам Discord.
- `/inventory.html?player=Ник` проверяет fingerprint предмета перед изъятием. Предмет сохраняется в служебное хранилище. `PENDING`/`RETURNING` после аварии требуют ручного разбора; автоматическая повторная выдача запрещена.

## Права и API

Новые права: `VIEW_PLAYER_IP`, `VIEW_PLAYER_INVENTORY`, `CONFISCATE_ITEMS`, `RESTORE_ITEMS`, `FREEZE_PLAYERS`, `TELEPORT_PLAYERS`, `CHANGE_GAMEMODE`, `KICK_PLAYERS`, `KILL_PLAYERS`. Действующие сессии каждый запрос получают актуальную роль и статус аккаунта.

`LoveWebAdminAPI.banPlayer(..., BanOrigin)` принимает явный источник игрового бана `STAFF`, `ANTICHEAT`, `CONSOLE`, `UNKNOWN` (`SECURITY` зарезервирован для нативного адаптера и отклоняется игровым finalizer) и идентификатор внешнего события для подавления повторов. Источник не определяется по тексту причины. Существующие сигнатуры сохранены. Старые записи отображаются с неизвестным источником и исходным автором. Создание тикетов также проходит через очередь; временные ошибки повторяются, а не теряют обращение.

**Важно:** автоматические источники требуют вызова нового API самим производителем наказания. Эта версия не приписывает обычному console-бану происхождение от Vesuvio или LoveAuth. Нативные ограничения безопасности LoveAuth не снимаются обычным разбаном: одобрение таких записей блокируется с объяснением необходимости работы через раздел безопасности.

## Данные и проверка

Перед изменением основной схемы создаётся SQLite snapshot `database-before-moderation-v2.db`; дела, ключи доступа, очередь Discord и изъятые предметы хранятся в `moderation.db`. Копировать работающие SQLite-файлы без WAL небезопасно; используйте остановку сервера или штатный SQLite backup.

Покрыты тестами: доступ по ключу, конкурирующее взятие дела, изоляция заметок, повторы сообщений, восстановление очереди, однократное резервирование возврата, остановка главного диспетчера, переполнение и отмена фоновой работы, ограничение подачи обращений. Проверка настоящих Discord permissions, кнопок, rate limits, ItemsAdder/DeluxeCombat и визуальная проверка Paper/Purpur требуют живого стенда.

## Оставшаяся часть большого плана

Этот PR реализует основу потоков, контроль доступа, дела/апелляции, Discord и безопасное изъятие. Не считать завершёнными: изменение срока наказания из апелляции; объединение дел; публичный запрос уточнений по жалобе; тихие часы и эскалацию по сменам; полностью настраиваемые шаблоны с предпросмотром; автоматические адаптеры наказаний Vesuvio/LoveAuth; полноценный журнал экономических транзакций всех Love-плагинов; веб-редакторы NPC/порталов/голограмм/путевых столбов; полноценный переход SQLite на раздельные очереди чтения и записи. Центр состояния Love-плагинов исключён по просьбе владельца.
