# Редактор игрового содержимого

Раздел «Игровое содержимое» редактирует определения, не прогресс или инвентари игроков.
Каталоги: простые контракты, цепочки контрактов, достижения, пометки LoveSubnames, оформление входа/выхода LE.
Редактора NPC здесь нет. Ключи существующих NPC и `@actor:...` используются только как цели этапов.

## Работа

1. Выбрать каталог, найти запись или создать ID. Доступно дублирование.
2. Настроить поля в форме. У цепочки добавлять, удалять и переставлять этапы; у диалога — узлы, реплики, ответы и переходы.
3. Связать записи на схеме. Нажатие карточки открывает её свойства.
4. Сохранить общий серверный черновик. Проверка показывает ошибки ссылок и циклы, затем запускает штатные парсеры владельцев.
5. Опубликовать. Проверяются базовая версия файлов и версия общего черновика; чужие правки дают конфликт 409.

Локальные несохранённые правки сохраняются при переключении разделов в рамках текущего сеанса. При перезагрузке браузера появляется предупреждение.
Для сохранности между сеансами используйте кнопку черновика. Черновик не применяется к серверу.
Свойства, для которых пока нет отдельного поля, можно изменить в раскрываемом JSON записи; основной интерфейс остаётся формой.
Предпросмотр текста заменяет `<player>` примером, не отправляет сообщения и не выполняет действия.

## Связи исполняются существующими механизмами

- **Контракт/цепочка → ачивка:** `completion-achievement`.
- **Ачивка → следующий контракт/цепочка:** `requires-achievement`.
- **Несколько ачивок → составная ачивка:** `trigger: {type: all-of, ids: [...]}`.
- **Ачивка → пометка:** `achievement` в определении пометки.
- **Ачивка → оформление входа/выхода:** `achievement` в стиле.

Для ачивки с метрикой используется штатный `counter`, например `contracts.completed`. Редактор не заменяет метрический триггер составным при случайном соединении: для такого условия создайте отдельную составную ачивку.
Пометка открывается по правилам LoveSubnames: если также заданы цена или permission, они продолжают действовать. Для бесплатной награды задайте `cost: 0` и пустое дополнительное право.
Оформление становится доступно для выбора игроком; редактор не меняет его текущий выбор автоматически.

Право на ачивку при завершении контракта записывается в той же транзакции SQLite, что и завершение. Повторная сдача не добавляет вторую награду.
Для вышедшего игрока оно остаётся в очереди `contract_achievement_rewards`; выдача через API `Achievements` повторяется после входа/доступности сервиса, примерно раз в пять секунд.
Публикация определений сама по себе не раздаёт деньги или предметы и не сбрасывает полученные ачивки.

## Файлы и применение

Редактор имеет фиксированные цели записи:

| Каталог | Владелец | Файл / раздел |
|---|---|---|
| Контракты | LoveContracts | `contracts.yml / contracts` |
| Цепочки | LoveContracts | `npc_stories.yml / npc_quests` |
| Ачивки | LoveEssential | `modules/achievements/achievements.yml / catalog` |
| Пометки | LoveSubnames | `config.yml / tags` |
| Вход/выход | LoveEssential | `modules/joinquit/joinquit.yml / styles` |

Меняется только соответствующий раздел, остальные настройки остаются. YAML при сохранении сериализуется заново, поэтому форматирование и часть комментариев могут измениться.
Пометки загружаются с учётом поставляемого каталога. При его редактировании эффективный список сохраняется явно, с `tags-defaults: false`, чтобы удалённая пометка не возвращалась из JAR.
У управляемого каталога стилей устанавливается `content-editor-owned: true`: LE не добавляет удалённые стили обратно из стандартного файла.

Публикация проверяет определения публичным методом `validateContentDefinitions`, после записи вызывает `reloadContentDefinitions` соответствующих плагинов.
Нужны обновлённые версии LoveContracts, LoveEssential и LoveSubnames из этого изменения, с актуальным LoveCore (API Achievements); старый/отсутствующий владелец помечается недоступным.
Для уже выполняемых контрактов нельзя удалить определение или менять условия/порядок этапов. Создайте новую версию под другим ID.

До записи сохраняется предыдущий набор определений в `LoveWebAdmin/content-editor/history`. Файлы заменяются атомарно по отдельности.
Если запись или применение не удались, восстанавливаются оригинальные файлы и перечитываются старые определения; ошибка возвращается клиенту, а не маскируется успешным сохранением.
История показывает до 50 последних публикаций. Восстановление создаёт черновик предыдущих определений и требует отдельной публикации.
Откат определений не отбирает уже полученные игроками награды.

## Доступ и API

- `VIEW_CONTENT` — просмотр каталогов, схемы и истории.
- `MANAGE_CONTENT` — редактирование, проверка, черновики и восстановление в черновик.
- `PUBLISH_CONTENT` — применение на сервере; включает необходимые права редактирования/просмотра в редакторе ролей.

Управляющий видит раздел автоматически. Другим существующим ролям права нужно выдать явно.

`GET /api/content/catalogs`, `/draft`, `/history`.
`POST /api/content/validate`, `/draft`, `/publish`, `/restore`.
Тело черновика/публикации содержит `revision`, `draftVersion`, `catalogs` со всеми пятью каталогами.
Клиент не может передать произвольный путь файла. NPC, консольные команды, данные игроков и секреты в этом API не редактируются.

## Проверка

Выполнены отдельные Java-тесты графа, файлового отката, сохранности активных определений и транзакционной очереди ачивок; JS-тесты модели и браузерные сценарии редактора.
Preview использует только синтетические каталоги. Его публикация не меняет настоящий сервер.
Полная Maven-сборка на Java 25 прошла: 336 Java-тестов без ошибок. Также прошли 29 JS-тестов и все 99 браузерных сценариев Playwright на Chromium. Игровое применение каталогов со всеми плагинами-владельцами нужно дополнительно проверить на тестовом сервере.
